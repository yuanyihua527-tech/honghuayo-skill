# 按业务约束选工具并对接现有系统

## R — 原文依据

> “我们就会结合他们现有的一些工具”

00:47:43，P0279，外贸客户已有飞书，使用多维表格整理询价单并通过智能体存取数据。另见 P0262–P0268，00:41:34–00:44:09：按效果要求和成本选择工具；P0612–P0617，01:29:49–01:31:00：数据外发、稳定性和费用顾虑。

## I — 方法解释

先看业务已有的工具、数据和使用习惯，再决定新增什么。
已有表格、配置或普通自动化能够完成的任务，不必直接开发复杂平台。
比较的是整个工作能否完成、复核负担和运行成本，而不只是模型单次演示。
本地界面、文件放本机、推理本地运行是不同事实；需要沿真实数据流逐项确认。
权限、日志、异常恢复和可用接口检查是实施补充，会议没有给出某产品的确定保证。

## A1 — 原文案例

外贸客户已用飞书，讲者在现有多维表格构建询价单，并用智能体录入、查询。P0279，00:47:43。未披露生产权限、字段映射、错误率和收益。

商品图演示使用免费工具，讲者也说更精细场景需人工调整，P0262–P0268。不能外推成具体工具长期免费或“可替代所有美工”。

## A2 — 适用与区分

- 适用：选模型或工具；已有 ERP/CRM/表格需对接；比较配置与定制；担心本地、数据外发、稳定性和费用。
- 语言信号：集成、选型、现有系统、build or buy、data flow、local deployment。
- 工作目标未定先用 demand-discovery；工作台的角色、状态和操作设计用 workbench-design。本卡不负责猜当前产品价格和功能。

## E — 执行

输入：具体任务、现有系统、样本、质量/成本限制、数据允许范围。缺许可或接口能力时先输出待验证项与可离线演示方案。

1. 列出任务中可由现有功能、确定性代码和模型分别完成的部分；优先保留用户已经选择且能满足任务的环境。
2. 对可行路径比较效果、复核/维护工作、连接条件、部署依赖和总成本。需要现价或当前功能时查官方资料或在实际环境验证，并标日期；不沿用会议中的产品承诺。
3. 画出“数据来源→处理端→模型端点→输出系统→日志/备份”清单，注明读写权限和负责人。接口未知写未知，不用“本地”概括整条链路。
4. 先用允许的样本验证读取、处理和输出；写入、发消息、发布、预约等动作保持项目既有授权边界。未授权时生成草稿或模拟结果。
5. 检查缺字段、鉴权失败、超时、重复处理、错误输出及人工接管；操作和记录字段用 operations.md。质量或成本不满足约定时切换更简单路径、缩小范围或暂缓。

输出：方案对比、推荐理由、数据流、依赖与未知项、样本验证和恢复路径。完成标准：业务方知道为何选此路径，实施者知道还需验证哪些连接条件。

## B — 边界

不保证个人微信自动操作不会封号；不把“模型在本地”推断成所有日志与数据都不外发。不能因文稿展示过某产品就认定它现在仍有同样能力。仅问某 API 参数或要求写普通代码时，直接完成该技术任务，不扩成企业转型咨询。

相关能力：与 workflow-distillation 组合确定接口前后的业务规则；与 delivery-adoption 组合移交运行维护。
